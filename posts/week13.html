CNN에서 ViT까지, 이미지를 보는 두 가지 방식

이번 주 학습 내용

몇 주 동안 텍스트와 LLM 쪽만 붙잡고 있다가, 이번 주엔 다시 이미지로 돌아왔다. 멀티모달로 넘어가기 전에 "모델이 이미지를 어떻게 보는가"부터 정리하는 흐름이었다. CNN으로 필터가 실제로 뭘 배우는지 눈으로 확인하고, YOLO로 이미지 안에서 물체의 위치까지 찾아본 뒤, 마지막엔 트랜스포머로 이미지를 읽는 ViT까지 이어졌다. 같은 주에 팀 프로젝트 통합 작업까지 겹쳐서, 이미지 모델과 RAG 서비스를 번갈아 붙잡은 한 주였다.

01. CNN 다시 보기 — 필터와 특성맵을 눈으로

CNN 자체는 Week 7에서 한 번 다뤘기 때문에 합성곱·풀링·Flatten 흐름은 복습에 가까웠다. FashionMNIST에 합성곱 층 두 개짜리 모델을 학습시켜 테스트 정확도 0.9184가 나왔고, 컬러 이미지인 CIFAR10에는 합성곱 블록 세 개에 ReduceLROnPlateau로 학습률을 줄여가는 모델을 붙여 0.7830이 나왔다. 흑백 28×28에서 컬러 32×32로만 바뀌어도 난이도가 꽤 올라간다는 게 숫자로 보였다.

이번에 새로 해본 건 학습된 모델의 안쪽을 들여다보는 것이었다. 학습 전 모델과 학습 후 모델의 conv1 필터를 나란히 그려보니, 학습 전엔 대부분 회색에 가까운 흐릿한 무작위 값이었던 3×3 필터들이, 학습 후엔 검정과 흰색이 뚜렷하게 갈린 대비 강한 모양으로 바뀌어 있었다. 중간 층의 출력(특성맵)은 register_forward_hook으로 순전파 도중에 가로채서 꺼냈다.

class FeatureExtractor: def __init__(self, model, layer_name): layer = dict(model.named_modules())[layer_name] layer.register_forward_hook(self.hook) # 순전파 때 출력 가로채기 def hook(self, module, input, output): self.features = output feature_maps = FeatureExtractor(model, 'conv1').get_features(inputs) # (1, 64, 28, 28)

앵클부츠 이미지 한 장을 넣고 conv1의 64장 특성맵을 펼쳐보니, 같은 신발인데도 어떤 맵은 밑창의 가로선을, 어떤 맵은 신발 끈 쪽 세로 윤곽을, 또 어떤 맵은 배경 영역을 밝게 잡고 있었다. 필터마다 반응하는 부분이 다르다는 설명이 그림 한 장으로 바로 이해됐다. conv2(32장, 26×26)도 신발 형태는 남아 있었지만 강조되는 부분이 조금씩 더 잘게 쪼개진 느낌이었다. 사전학습 모델 쪽은 ResNet18의 파라미터를 전부 동결하고 마지막 fc만 CIFAR10용 10클래스로 바꿔 끼운 뒤 EarlyStopping을 거는, Week 7에서 했던 전이학습을 한 번 더 따라가는 정도였다.

02. YOLO v11 — 무엇이, 어디에

분류가 "이 사진이 뭔가"였다면, 객체 탐지는 "사진 안에 뭐가 어디에 있나"를 묻는다. YOLO(You Only Look Once)는 이름 그대로 이미지를 한 번만 보고 끝낸다. 이미지를 그리드로 나누고, 각 칸이 경계 상자와 신뢰도, 클래스 확률을 동시에 예측한 다음, 겹치는 상자들은 NMS(Non-Maximum Suppression)로 정리하는 구조다.

from ultralytics import YOLO model = YOLO('yolo11n') results = model('https://ultralytics.com/images/bus.jpg') results[0].save(filename='results/bus_yolo.jpg') boxes = results[0].boxes # cls(클래스 id), conf(신뢰도), xyxy(좌상단·우하단 좌표)

버스 사진과 도심 교차로 사진에 돌려보니 사람·버스·자동차에 상자가 바로 그려졌고, 결과 객체에서 xyxy(픽셀 좌표), xywhn(정규화 좌표), conf, cls를 하나씩 뜯어봤다. 영상 파일에도 같은 모델을 그대로 넣어 프레임마다 탐지해봤고, 이어서 OpenCV로 상자를 직접 그리려고 80개 클래스별 색까지 뽑아뒀는데, 탐지 결과를 그리는 함수는 틀만 잡아두고 마무리하지 못했다. 지난주 해커톤에서 이미 YOLO를 학습·경량화까지 해봤는데, 그땐 급하게 쓰느라 넘겼던 결과 객체의 속성들을 이번엔 차근차근 짚고 넘어갈 수 있었다.

03. ViT — 이미지를 16×16 단어로

마지막은 Vision Transformer였다. 이미지를 16×16 픽셀 패치로 잘라서 각 패치를 문장의 토큰처럼 다루는 모델이다. 패치를 펼쳐 임베딩하고, 위치 정보를 더하고, 맨 앞에 CLS 토큰을 붙여 Transformer Encoder에 통과시킨 뒤, CLS 토큰의 출력으로 분류한다. 합성곱으로 작은 영역부터 차근차근 보는 CNN과 달리, 처음부터 패치끼리 서로를 참고하면서 이미지 전체의 관계를 본다는 점이 달랐다.

processor = ViTImageProcessor.from_pretrained('google/vit-base-patch16-224') model = ViTForImageClassification.from_pretrained('google/vit-base-patch16-224') outputs = model(**processor(images=image, return_tensors='pt')) print(model.config.id2label[outputs.logits.argmax(-1).item()]) # Egyptian cat

ImageNet-21k로 사전학습하고 1k로 미세조정한 google/vit-base-patch16-224에 COCO의 고양이 사진을 넣으니 1000개 클래스 로짓 중 "Egyptian cat"이 나왔다. 같은 모델을 pipeline('image-classification')으로도 불러봤는데, Week 10에서 텍스트 태스크에 쓰던 그 pipeline이 이미지에도 똑같은 모양으로 붙는 게 반가웠다. 대신 ViT는 CNN보다 사전학습에 훨씬 많은 데이터가 필요하고, 데이터가 방대할수록 CNN보다 앞선다는 설명도 함께 들었다.

KPT 회고

Keep

팀 프로젝트 통합이 한창인 주였는데도 CNN → YOLO → ViT로 이어지는 수업 흐름을 놓치지 않고 따라갔다. 특히 Week 7에서 결과 숫자만 보고 넘어갔던 CNN을, 이번엔 필터와 특성맵을 직접 그려보면서 "안에서 무슨 일이 일어나는지"까지 확인한 게 좋았다.

Problem

ViT는 사전학습 모델을 불러와 추론만 해봤다. 패치로 자르고, 임베딩하고, 위치 정보와 CLS 토큰을 붙이는 과정을 그림과 설명으로만 이해했지 코드로 직접 만들어보지는 못했다. CNN은 층을 직접 쌓아봐서 shape 변화가 머릿속에 그려지는데, ViT는 아직 그 감이 없다.

Try

작은 이미지 하나로 패치 분할 → 임베딩 → 위치 정보 더하기까지 직접 구현해보면서 텐서 shape을 따라가볼 생각이다. 가능하면 CNN 특성맵을 그렸던 것처럼 ViT의 어텐션도 시각화해서 둘이 이미지를 어떻게 다르게 보는지 비교해보고 싶다.

새롭게 발견한 것

필터는 처음부터 뭔가를 알고 있는 게 아니었다. 학습 전 필터는 말 그대로 흐릿한 무작위 숫자였고, 뚜렷한 명암 패턴은 학습을 거친 뒤에야 생겼다. "CNN이 특징을 추출한다"는 말을 그동안 당연하게 써왔는데, 그 특징조차 데이터에서 배운 결과라는 게 학습 전/후 필터를 나란히 놓고 나서야 실감났다.

YOLO는 "무엇"과 "어디"를 한 번에 본다. 위치를 먼저 찾고 그다음 분류하는 게 아니라, 그리드의 각 칸이 상자와 클래스를 동시에 예측하고 중복만 NMS로 정리한다. 실시간 영상에서도 빠르게 돌아가는 이유가 이 구조 자체에 있었다.

트랜스포머는 텍스트 전용이 아니었다. 이미지를 16×16 패치로 자르면 그게 곧 토큰이 되고, 그 뒤는 Week 9에서 봤던 Encoder 구조를 거의 그대로 쓴다. 입력을 "토큰의 나열"로만 바꿔주면 같은 틀을 문장에도 이미지에도 쓸 수 있다는 게, 다음에 배울 멀티모달로 넘어가는 다리처럼 느껴졌다.

프로젝트 진행 과정

이번 주는 3차 팀 프로젝트의 통합 주간이기도 했다. 주제는 청년·1인 창업자를 위한 AI 행정·재정 지원 플랫폼 "창업ON"이다. 세금·세액감면 조건이나 정부·지자체 지원사업이 여러 곳에 흩어져 있어 스스로 찾고 판단하기 어렵다는 문제에서 출발했고, 세무 Q&A, 청년창업 세액감면 판정, 맞춤 지원정책 탐색, 공고문 분석, 영수증 정보 추출을 핵심 기능으로 잡았다.

  • 구성 — FastAPI Backend, LangChain·LangGraph 기반 LLM 서버, PostgreSQL + pgvector, React + Vite Frontend를 Docker Compose로 묶었다. 질문은 LangGraph에서 정책·공고·세금 경로로 나뉘고, 세금 경로는 근거가 충분해질 때까지 검색을 반복하는 멀티홉 구조다. 세액감면 판정 자체는 LLM이 아니라 Backend의 규칙 엔진이 맡고, LLM은 근거 설명과 법령 인용만 담당하도록 역할을 나눴다
  • 진행 — 첫 주에 유스케이스·ERD·API 명세 같은 설계 문서를 먼저 맞춘 뒤, 데이터 수집·Backend·LLM·Frontend를 각자 feature 브랜치에서 병렬로 개발했다. 이번 주엔 이걸 develop으로 합치면서 서비스 간 연결, 통합 이슈 정리, 인증 토큰 관련 보안 문제 제거, 프론트 도커화와 nginx 배포 구성까지 진행했다. 병합 중에 충돌을 파일 단위로 덮어써서 연동 로직이 통째로 사라졌다가 복구하는 일도 있었다
  • 성능 개선 — Dense + BM25를 RRF로 합치고 Cohere Rerank로 재정렬하는 하이브리드 검색에, 사용자 조건을 반영한 검색어 보강과 법령 조문 후속 검색을 더해 정책 검색 R@5를 64.3%에서 70%대로, 세금 턴 통과율을 66.1%에서 77.4%로 올렸다. 근거 판정 LLM 호출을 줄이면 평균 5초 정도 빨라졌지만 통과율이 11%p 넘게 떨어져서, 세금 답변은 정확도를 우선하기로 하고 긴 대기 시간은 화면에 진행 상태를 보여주는 방식으로 보완했다

지난주 Problem에 "RRF, Rerank, Multi-hop을 전부 개별 예제로만 확인했다"고 적었는데, 이번 프로젝트에서 그걸 한 파이프라인에 같이 얹어보게 됐다. 기법 하나를 붙일 때마다 평가셋을 다시 돌려 숫자로 확인해야 했고, 빠르게 만드는 것과 정확하게 만드는 것 사이에서 결국 팀이 기준을 정해야 한다는 걸 직접 겪었다.

다음 주 목표

  • ViT의 패치 분할·임베딩·위치 정보 추가 과정을 직접 구현하고 텐서 shape 따라가보기
  • 이미지 분류·탐지에 이어지는 다음 진도, 이미지와 텍스트를 함께 다루는 멀티모달 모델로 넘어가기
  • 팀 프로젝트 남은 이슈(공고문 요약 화면 부재, 프론트 요청 타임아웃) 정리하고 최종 코드 기준으로 세금 평가 한 번 더 돌려보기
  • 프로젝트 발표 준비 — 성능 개선 과정과 "정확도 우선" 결정의 근거를 숫자 중심으로 정리하기
결과 숫자만 보던 CNN의 안쪽을 들여다보고, 같은 트랜스포머가 이미지도 읽는다는 걸 확인한 한 주였다.
프로젝트에서는 따로 배웠던 검색 기법들을 한데 얹어보면서, 빠른 것과 정확한 것 사이의 선택이 결국 사람 몫이라는 걸 배웠다.
