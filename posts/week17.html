01. 세션과 쿠키 — HTTP가 잊어버리는 걸 붙잡는 두 방법

HTTP는 요청 하나에 응답 하나를 주고 나면 상대를 잊어버린다. 이걸 무상태성이라고 한다. 로그인을 유지하려면 매번 "나 아까 그 사람"이라는 걸 알려줄 방법이 필요한데, 그 방법이 세션과 쿠키다.

  • 세션 — 데이터는 서버 DB에 두고, 브라우저에는 열쇠인 sessionid만 준다. 짐을 맡기고 번호표만 들고 다니는 느낌
  • 쿠키 — 데이터 자체를 브라우저에 두고, 요청할 때마다 같이 보낸다

Django에서 request.session을 바로 쓸 수 있는 건 SessionMiddleware 덕분이다. 요청이 들어오면 sessionid 쿠키로 django_session 테이블을 찾아 딕셔너리로 붙여주고, 응답이 나갈 때 바뀐 내용을 다시 저장한다. 테이블은 session_key, session_data, expire_date 세 컬럼뿐이다. 저장할 때 JSON으로 바꾸기 때문에 datetime 같은 객체는 문자열로 바꿔서 넣어야 한다.

def set_session(request): request.session['username'] = request.POST.get('username') request.session['nums'] = [1, 2, 3, 4, 5] request.session['data'] = { 'message': 'Hello, Django Session', 'today': datetime.now().strftime('%Y-%m-%d %H:%M:%S') # 문자열로 } return redirect('app:index') def modify_session(request): request.session['favorite_color'] = 'springgreen' # 최상위 키 교체 → 자동 감지 request.session['nums'].append(999) # 리스트 내부 변경 → 감지 못 함 request.session['data']['new_item'] = 'new_item' request.session.modified = True # 그래서 직접 표시 del request.session['point'] # 키 하나만 삭제 return redirect('app:index') def delete_session(request): request.session.flush() # 전체 삭제 + 새 sessionid 발급 return redirect('app:index')

Django는 최상위 키에 새 값을 넣을 때만 변경을 알아챈다. 리스트에 append하거나 안쪽 딕셔너리 값을 바꾸면 모르고 넘어가서, modified = True를 직접 붙여줘야 저장된다. 삭제도 두 가지가 있다. del은 키 하나만 지우고 sessionid는 그대로 두지만, flush()는 DB 레코드까지 지우고 새 ID를 발급한다. 로그아웃에 flush()를 쓰는 이유는 혹시 탈취된 sessionid가 있더라도 더는 쓸 수 없게 만들기 위해서다. 만료 시간을 정하는 set_expiry()는 세션을 만드는 view에서 한 번만 불러야 한다. 매 요청마다 불리는 index에 두면 타이머가 계속 리셋돼서 사실상 만료되지 않는다.

쿠키는 쓰는 위치가 달랐다. 세션은 request에 쓰지만, 쿠키는 응답 헤더의 Set-Cookie로 전달되기 때문에 response 객체를 먼저 만들고 거기에 설정해야 한다. 읽을 때는 request.COOKIES.get()으로 읽는다.

response = redirect('app:index') response.set_cookie( name, value, path='/app/', max_age=120, httponly=True, # JS의 document.cookie로 못 읽음 → XSS 대비 samesite='Lax', # 다른 사이트에서 보내는 POST에는 쿠키를 안 실음 → CSRF 대비 secure=False # True면 HTTPS에서만 전송 (개발 중이라 False) ) return response

정리하면 로그인 상태나 장바구니처럼 민감한 건 세션에, 테마 설정이나 "오늘 하루 안 보기" 같은 가벼운 값은 쿠키에 둔다.

02. 대화를 DB에 남기는 챗봇 — 대화 기록을 직접 만든 저장소에

세션 다음은 같은 아이디어를 챗봇에 적용한 실습이었다. IT 직업상담 챗봇인데, 대화 내용을 메모리가 아니라 Django 모델에 저장해서 서버를 껐다 켜도 이어서 대화할 수 있게 만든다.

class ChatMessage(models.Model): session_id = models.CharField(max_length=255, db_index=True) message_type = models.CharField(max_length=10, choices=[('human', 'Human'), ('ai', 'AI')]) content = models.TextField() created_at = models.DateTimeField(auto_now_add=True) class Meta: ordering = ['created_at']

핵심은 LangChain의 BaseChatMessageHistory를 상속해서 대화 기록 저장소를 직접 만드는 부분이었다. messages, add_message, clear 세 개만 ORM으로 채우면 된다.

class DatabaseChatMessageHistory(BaseChatMessageHistory): def __init__(self, session_id): self.session_id = session_id @property def messages(self): messages = [] for m in ChatMessage.objects.filter(session_id=self.session_id): messages.append(HumanMessage(content=m.content) if m.message_type == 'human' else AIMessage(content=m.content)) return messages def add_message(self, message): message_type = 'human' if isinstance(message, HumanMessage) else 'ai' ChatMessage.objects.create(session_id=self.session_id, message_type=message_type, content=message.content) def clear(self): ChatMessage.objects.filter(session_id=self.session_id).delete() chain_with_history = RunnableWithMessageHistory( prompt | llm, get_session_history=lambda session_id: DatabaseChatMessageHistory(session_id), input_messages_key='query', history_messages_key='history' )

프롬프트에 MessagesPlaceholder('history') 자리를 만들어두면, RunnableWithMessageHistory가 호출 전에 messages로 이전 대화를 꺼내 끼워 넣고, 호출 후에는 질문과 답변을 add_message로 저장한다. 어떤 대화인지는 config={'configurable': {'session_id': ...}}로 알려준다.

view 쪽은 대화 하나를 관리하는 API 다섯 개로 나뉘었다. 새 대화는 uuid4()로 ID를 만들어 돌려주고, 질문은 그 ID와 함께 보낸다. 대화 목록은 지난주에 배운 values().annotate()로 세션별 첫·마지막 메시지 시간과 개수를 묶어서 만들고, 복원은 해당 ID의 기록을 JSON으로 돌려준다. 삭제는 @require_http_methods(['DELETE'])로 DELETE 요청만 받게 했다.

화면 쪽은 TODO 주석만 있는 함수를 채우는 방식이었는데, 지난주에 실습 파일만 만들어두고 넘어갔던 async/await를 여기서 제대로 써봤다.

async function sendMessage() { const query = document.querySelector('#user-input').value.trim(); addMessage(query, true); try { showLoading(true); const formData = new FormData(); formData.append('query', query); formData.append('session_id', sessionId); const response = await fetch("{% url 'app:chatbot' %}", { method: 'POST', body: formData }); if (response.ok) { const { content } = await response.json(); addMessage(content, false); } } catch { showChatStatus('네트워크 오류가 발생했습니다.', 'error'); } finally { showLoading(false); } }

.then()을 이어 붙이던 것보다 위에서 아래로 그대로 읽혀서 훨씬 편했다. FormData를 body에 그대로 넣으면 Content-Type도 알아서 맞춰지고, 서버에서는 request.POST.get()으로 받는다. 반면 복원·삭제는 JSON.stringify()로 보내서 서버에서 json.loads(request.body)로 꺼냈다. 보내는 형식에 따라 받는 쪽 코드도 달라진다.

03. boto3로 S3에 파일 올리기

지금까지 업로드한 파일은 Django 프로젝트 폴더 안에 쌓였는데, 이번에는 AWS의 파일 저장소인 S3에 올렸다. 파이썬에서 AWS를 다룰 때는 공식 SDK인 boto3를 쓴다. AWS API와 1:1로 대응하는 Client와 객체처럼 다루는 Resource 두 가지 방식이 있는데, 실습은 Client로 진행했다.

먼저 IAM에서 S3 권한을 가진 사용자를 만들고 액세스 키를 발급받아 .env에 넣는다. 코드에는 키 값을 직접 쓰지 않고 환경변수로만 읽는다.

class S3Client: def __init__(self): self.s3 = boto3.client( 's3', aws_access_key_id=settings.AWS_ACCESS_KEY_ID, aws_secret_access_key=settings.AWS_SECRET_ACCESS_KEY, region_name=settings.AWS_S3_REGION_NAME ) self.bucket_name = settings.AWS_STORAGE_BUCKET_NAME def upload(self, file): date_prefix = datetime.now().strftime('%Y%m%d_%H%M%S') key = f'uploads/{date_prefix}{file.name}' # 같은 이름 덮어쓰기 방지 self.s3.upload_fileobj( file, self.bucket_name, key, ExtraArgs={'ContentType': file.content_type} ) return f'https://{self.bucket_name}.s3.amazonaws.com/{key}'

단독 스크립트에서는 로컬 경로를 받는 upload_file()을 썼고, Django에서는 사용자가 올린 파일 객체를 그대로 넘기는 upload_fileobj()를 썼다. ContentType을 같이 넣지 않으면 브라우저에서 URL을 열었을 때 이미지가 보이지 않고 다운로드되는 경우가 있다고 한다.

def upload_file(request): if request.method == 'POST': form = FileUploadForm(request.POST, request.FILES) if form.is_valid(): model = form.save(commit=False) model.file = s3_client.upload(form.files['file']) # 파일 대신 S3 URL을 저장 model.save() return redirect('app:upload')

지난주 게시판에서 작성자를 채울 때 쓴 commit=False가 여기서도 나왔다. 저장을 잠깐 미뤄두고 파일 필드에 S3 URL을 넣은 뒤 저장한다. 업로드 결과 링크는 messages.success()에 HTML로 담고, 템플릿에서 {{ message.message|safe }}로 태그가 그대로 출력되게 했다.

04. 두 서버로 나눈 챗봇 — Django는 얼굴, FastAPI는 두뇌

02의 챗봇은 Django 하나가 화면, 저장, LLM 호출을 모두 맡았다. 이번에는 이걸 두 서버로 나눴다. 8000번 Django는 채팅 화면과 대화 기록 저장을, 8001번 FastAPI는 LangChain으로 OpenAI를 부르는 일만 한다. 터미널 두 개를 열어 각각 띄워두고 시작한다.

[브라우저] ── fetch ──▶ [Django :8000] ── DB 저장 │ requests.post() ▼ [FastAPI :8001] ── LangChain ──▶ [OpenAI]

브라우저는 FastAPI를 직접 모르고 Django에만 요청한다. Django view가 받은 메시지를 requests.post()로 FastAPI에 넘기고, 돌아온 답을 질문과 함께 DB에 저장한 뒤 브라우저에 돌려준다.

# Django — chat/views.py response = requests.post( f"{settings.FASTAPI_SERVICE_URL}/chat/", json={'message': user_message, 'session_id': session_id}, timeout=30 ) if response.status_code == 200: bot_response = response.json().get('response', '') ChatMessage.objects.create(session_id=session_id, message_type='human', content=user_message) ChatMessage.objects.create(session_id=session_id, message_type='ai', content=bot_response)

FastAPI 쪽은 Week 14에 모델 서빙으로 한 번 써봐서 구조가 익숙했다. 이번에 새로 붙은 건 라우터를 include_router(prefix='/chat')로 나눈 것, 다른 포트의 요청을 허용하는 CORSMiddleware, 그리고 Pydantic 모델에 Field(min_length=1, max_length=2000)처럼 검사 조건을 붙인 것이다. LLM 호출은 await runnable_with_history.ainvoke()로 비동기로 했다.

재미있었던 건 대화 기록을 두 군데에 둔다는 점이다. FastAPI는 기록을 InMemoryChatMessageHistory, 즉 메모리에 두기 때문에 서버를 재시작하면 다 사라진다. 그래서 Django가 DB에 영구 저장해두고, 사용자가 ?session_id=...로 이전 대화에 들어오면 DB 기록을 FastAPI의 /chat/history/set에 다시 넣어준다.

# FastAPI — DB에서 온 이력을 메모리에 다시 채우기 def set_history(self, session_id, items): self.session_stores[session_id] = InMemoryChatMessageHistory() for item in items: if item['type'] in ('human', 'user'): self.session_stores[session_id].add_user_message(item['content']) elif item['type'] in ('ai', 'assistant'): self.session_stores[session_id].add_ai_message(item['content'])

02는 LangChain이 DB를 직접 읽고 쓰게 만들었고, 04는 LangChain은 메모리만 보고 Django가 DB와 메모리 사이를 맞춰준다. 같은 기능인데 어느 서버가 무엇을 책임지느냐에 따라 코드 위치가 완전히 달라지는 게 흥미로웠다. 대신 서버가 둘이라 FastAPI를 안 켜두면 Django 쪽에서 연결 오류가 나고, 어디서 문제가 생겼는지 터미널 두 개의 로그를 같이 봐야 했다.

05. EC2에 Django 올리기 — 내 컴퓨터 밖에서 열리는 첫 페이지

마지막 날은 클라우드였다. 프리티어 계정으로 EC2 인스턴스를 만들고, 네트워크는 따로 구성하지 않고 기본 VPC를 그대로 썼다. 인스턴스를 껐다 켜면 퍼블릭 IP가 바뀌기 때문에 탄력적 IP를 하나 받아 인스턴스에 연결해 주소를 고정했다.

올린 프로젝트는 버튼 하나와 CSS 하나가 있는 아주 단순한 Django 페이지였다. 코드는 GitHub에 올린 뒤 서버에서 clone하거나, FileZilla로 키 파일을 써서 접속해 폴더째 옮기는 두 방법을 다 해봤다. 서버에서는 가상환경을 만들고 requirements.txt로 패키지를 설치한 뒤 개발 서버를 띄웠다.

python3 -m venv .venv source .venv/bin/activate pip install -r requirements.txt python manage.py runserver 0.0.0.0:8000

0.0.0.0으로 띄워야 외부에서 들어오는 요청도 받는다. 그리고 AWS 쪽에서도 문을 열어줘야 해서, 보안 그룹 인바운드 규칙에 8000번 포트를 추가했다. 마지막 관문은 Django의 ALLOWED_HOSTS였다. 로컬과 서버가 같은 코드를 쓰니, 컴퓨터 이름으로 구분해서 값을 다르게 줬다.

import socket if socket.gethostname() == 'playdata': # 실습실 PC 이름 ALLOWED_HOSTS = ['127.0.0.1', 'localhost'] else: # EC2 ALLOWED_HOSTS = ['<탄력적 IP>'] STATICFILES_DIRS = [BASE_DIR / 'static'] STATIC_ROOT = BASE_DIR / 'staticfiles'

브라우저 주소창에 탄력적 IP와 8000번 포트를 입력해서 "배포된 Django 웹 서버" 문구가 뜨는 걸 확인했다. 아직은 개발용 runserver에 DEBUG = True 상태라 실제 서비스라고 하기는 어렵지만, 실습실 컴퓨터가 꺼져 있어도 열리는 페이지가 생겼다는 게 꽤 신기했다.

Keep

지난주에 배운 것들이 이번 주 실습에 계속 다시 나왔다. 챗봇 화면의 TODO를 채우면서 미뤄뒀던 async/await를 실제로 써봤고, 대화 목록은 annotate로, 파일 업로드는 commit=False로 풀었다. 새로 배운 것보다 이미 배운 걸 다른 자리에서 다시 꺼내 쓴 경우가 많아서, 한 번 보고 지나간 내용이 조금씩 손에 붙는 느낌이었다. 로컬에서만 돌리던 Django를 EC2에 올려 실제 IP로 열어본 것도 좋은 경험이었다.

Problem

AWS 쪽은 콘솔 화면을 따라 누르는 비중이 컸다. IAM 사용자, 보안 그룹, 탄력적 IP를 왜 그 순서로 설정하는지 아직 머릿속에 그림이 없다. 4일 동안 세션, 챗봇 두 개, S3, EC2까지 지나가서 챗봇 두 개의 구조 차이도 코드를 다시 펼쳐봐야 설명할 수 있는 수준이다. 그리고 지난주 Try였던 12_async_await.js는 챗봇에서 await를 써본 것과 별개로 여전히 비어 있고, ORM 문제와 게시판 다시 만들기도 손대지 못했다.

Try

02 챗봇과 04 챗봇을 나란히 놓고 "기록은 누가 저장하고, 누가 읽는가"를 그림 하나로 정리해볼 생각이다. AWS는 이번에 만든 리소스를 하나씩 다시 보면서 각각이 어떤 역할인지 적어두고, 실습이 끝나면 인스턴스 중지와 요금 확인을 습관으로 만들려 한다. 탄력적 IP는 인스턴스를 꺼둔 동안에도 요금이 나올 수 있다고 하니 특히 챙겨야겠다.

새롭게 발견한 것

만료된 세션은 저절로 지워지지 않는다. expire_date가 지나면 무효로 처리될 뿐, django_session 테이블의 행은 그대로 남는다. 계속 쌓이기 때문에 python manage.py clearsessions로 따로 정리해줘야 한다고 한다. 만료와 삭제가 별개라는 게 의외였다.

HTTP에는 쿠키를 지우는 명령이 없다. delete_cookie()는 같은 이름의 쿠키를 만료 시간이 과거인 값으로 다시 보내는 방식이다. 브라우저가 "이미 만료된 쿠키"로 보고 버리는 걸 이용한 것이다. 그래서 지울 때도 설정할 때와 같은 path를 맞춰줘야 같은 쿠키로 인식된다.

컴퓨터 이름 하나로 설정을 나눌 수 있다. 같은 settings.py를 로컬과 EC2에서 같이 쓰려고 socket.gethostname()으로 분기했다. 주피터 노트북에서 socket.gethostname()을 찍어보니 실습실 PC 이름이 그대로 나왔다. 간단하지만 PC 이름이 바뀌면 깨지는 방식이라, 나중에는 환경변수로 나누는 쪽이 더 안전할 것 같다.

트러블슈팅

문제 : S3 업로드에서 NoCredentialsError가 났다

단독 스크립트 boto3_s3_iam.py로는 업로드가 잘 됐는데, 같은 키로 Django에서 파일을 올리니 업로드가 실패하고 터미널에 자격 증명 에러가 찍혔다.

botocore.exceptions.NoCredentialsError: Unable to locate credentials

.env 파일도 있고 키 이름도 맞았다. S3Client 안에서 settings.AWS_ACCESS_KEY_ID를 찍어보니 None이었다. 원인은 settings.py 맨 아래였다. load_dotenv를 import만 해놓고 정작 호출하지 않아서, .env의 값이 환경변수에 올라가지 않은 상태로 os.environ.get()을 하고 있었다.

# 수정 전 import os from dotenv import load_dotenv AWS_ACCESS_KEY_ID = os.environ.get('AWS_ACCESS_KEY_ID') # None # 수정 후 import os from dotenv import load_dotenv load_dotenv() # .env 내용을 환경변수로 올림 AWS_ACCESS_KEY_ID = os.environ.get('AWS_ACCESS_KEY_ID')

스크립트에서는 맨 위에 load_dotenv()를 제대로 불러놨기 때문에 문제가 없었던 것이다. os.environ.get()은 값이 없어도 에러 없이 None을 돌려주니, 설정 단계에서는 조용히 지나가고 실제로 AWS에 요청하는 순간에야 터진다. 환경변수를 읽는 코드에서는 import만 보고 넘어가지 말고, 값이 실제로 들어왔는지 한 번 찍어보는 게 빠르다는 걸 배웠다.
