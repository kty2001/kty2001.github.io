01. GitHub 협업 흐름 — 이슈에서 PR까지

혼자 쓰던 저장소에서는 main에 바로 커밋하는 게 전부였는데, 이번엔 협업할 때의 순서를 한 바퀴 따라가봤다. 먼저 이슈 템플릿을 만들어두면 새 이슈를 열 때마다 같은 양식이 채워진다. 기능 요청 템플릿에는 문제 제기, 기능 요약, 상세 설명, 할 일 체크리스트, 비고 칸을 두었다.

--- name: Feature request about: Suggest an idea for this project --- **문제 제기** - 어떠한 문제로 해당 기능을 추가하려 하는지 설명해주세요. **할일 목록** - [ ] 할일1 - [ ] 할일2

그다음은 이슈 번호를 중심으로 움직였다. 3번 이슈를 열고, 이슈 번호가 들어간 feature/3-helloworld 브랜치에서 작업하고, 커밋 메시지에도 #3을 붙인 뒤 PR로 main에 합쳤다.

* Merge pull request #5 from kty2001/feature/3-helloworld |\ | * feat: #3 hello world 구현 완료 * | Update issue templates |/ * Initial commit

로그 그래프로 보니 브랜치가 갈라졌다가 PR로 다시 합쳐지는 모양이 그대로 남아 있었다. 커밋 메시지에 이슈 번호를 적어두면 GitHub에서 이슈와 커밋이 서로 링크된다는 것도 이번에 알았다. 나중에 "이 코드 왜 들어왔지?"를 추적할 때 이 연결이 꽤 쓸모 있을 것 같다.

02. DVC — 모델 파일은 git 밖에서 버전 관리

지난주에 만든 iris_model.joblib 같은 모델 파일은 용량이 크고 바이너리라서 git에 그대로 넣기 애매하다. DVC는 실제 파일은 git에서 빼고, 대신 그 파일을 가리키는 작은 메타 파일만 git에 커밋하게 해준다.

dvc init # DVC 관리 시작 dvc add model/iris_model.joblib # 모델 추적 → .dvc 파일 생성 git add model/iris_model.joblib.dvc .gitignore
# model/iris_model.joblib.dvc outs: - md5: 80d9d2458332f7ff4656967e817365d5 size: 367335 hash: md5 path: iris_model.joblib

.gitignore에는 model/*.joblib이 들어가고, git에는 해시와 크기만 적힌 .dvc 파일이 올라간다. 모델을 다시 학습해서 v2로 바꾼 뒤 dvc add를 다시 하면 이 해시가 바뀌고, 그 변경이 git 커밋으로 남는다. 결국 "어떤 코드 버전에 어떤 모델이 붙어 있었는지"를 git 히스토리로 따라갈 수 있게 되는 구조였다. 실제 파일 내용은 .dvc/cache 아래에 해시 이름으로 쌓여 있었다.

03. pytest와 TestClient — 서버 없이 API 테스트

자동화를 붙이기 전에 "무엇을 자동으로 확인할 것인가"부터 필요했다. FastAPI의 TestClient를 쓰면 uvicorn으로 서버를 띄우지 않고도 앱에 요청을 보내볼 수 있다.

from fastapi.testclient import TestClient from app.main import app client = TestClient(app) def test_health(): response = client.get('/health') assert response.status_code == 200 assert response.json()['status'] == 'ok'

함수 이름을 test_로 시작하게 만들어 tests/ 폴더에 두면 pytest가 알아서 찾아 실행한다. 루트 응답과 헬스 체크 두 개뿐인 작은 테스트였지만, 다음 단계에서 이게 "통과해야 배포된다"는 관문 역할을 하게 된다.

04. GitHub Actions — push 한 번에 테스트부터 배포까지

앞의 과정을 전부 묶은 게 .github/workflows/ci.yml이다. main에 push하거나 PR을 올리면 GitHub가 제공하는 Ubuntu 환경에서 정해진 단계를 순서대로 실행한다.

on: push: branches: [main] pull_request: branches: [main] permissions: contents: read # 저장소 읽기 권한만 jobs: test-and-build: runs-on: ubuntu-latest steps: - uses: actions/checkout@v7 - uses: actions/setup-python@v7 with: python-version: "3.12" - run: pip install -r requirements.txt - run: python train.py - run: python -m pytest - run: docker build -t iris-api:${{ github.sha }} .

코드 가져오기 → 파이썬 설치 → 라이브러리 설치 → 모델 학습 → 테스트 → 이미지 빌드 순서다. 중간에 테스트가 하나라도 실패하면 뒤 단계는 실행되지 않는다. 이미지 태그에 github.sha, 즉 커밋 해시를 붙여서 어떤 커밋으로 만든 이미지인지 바로 알 수 있게 한 것도 눈에 띄었다.

- name: Login to Docker Hub if: github.event_name == 'push' && github.ref == 'refs/heads/main' run: | echo "${{ secrets.DOCKER_TOKEN }}" | docker login \ -u "${{ secrets.DOCKER_USERNAME }}" --password-stdin

Docker Hub 로그인·태그·push 단계에는 if 조건이 붙어 있다. PR에서는 테스트와 빌드까지만 확인하고, 실제로 main에 합쳐졌을 때만 이미지를 올리는 구조다. 토큰은 저장소 설정의 Secrets에 넣어두고 secrets.DOCKER_TOKEN으로 꺼내 쓰기 때문에 파일 어디에도 값이 드러나지 않는다. 지난주에 손으로 하던 빌드를 이제 push가 대신 해주는 셈이다.

05. HTML — 화면에 올릴 내용을 구조로 적기

주 후반부터는 웹 화면으로 넘어갔다. HTML은 "어떻게 보일지"가 아니라 "무엇인지"를 적는 언어라는 설명에서 출발했다. 그래서 굵게 보이는 것만 같아도 <strong>은 중요한 내용, <em>은 강조, <mark>는 하이라이트처럼 의미가 다르고, 이렇게 의미를 맞춰 쓰면 스크린리더나 검색 봇이 내용을 제대로 해석할 수 있다.

  • 텍스트 — <p> 안의 줄바꿈과 연속 공백은 공백 하나로 합쳐지고, 그대로 보여주려면 <pre>. 태그 기호 자체는 &lt;, &gt; 같은 엔티티로 적는다
  • 목록·표 — ol/ul/dl(용어-설명), 표는 thead·tbody·tfoot로 행을 묶고 th/td로 셀을 구분
  • 전역 속성 — id는 페이지에서 유일, class는 그룹, 그 밖에 title(툴팁), data-*(사용자 정의), contenteditable
  • inline vs block — span은 옆으로 이어지고 div는 한 줄을 통째로 차지한다
<!-- 이미지 맵: 한 장의 이미지를 영역별로 다른 링크에 연결 --> <img src="../assets/image/img1.jpg" usemap="#imgmap"> <map name="imgmap"> <area shape="rect" coords="0,0, 100,200" href="https://naver.com"> <area shape="rect" coords="100,0, 200,200" href="https://google.com"> </map> <!-- 같은 영상을 여러 포맷으로 두면 브라우저가 재생 가능한 것을 고른다 --> <video controls> <source src="small.webm" type="video/webm"> <source src="small.mp4" type="video/mp4"> </video>

이미지는 경로와 크기 단위를 같이 봤다. ../로 시작하는 상대 경로와 /로 시작하는 절대 경로, 그리고 px는 고정 크기, %는 부모 기준 가변 크기라는 차이다. 링크는 target="_blank"로 새 탭 열기, #id로 같은 페이지 안 이동, iframe으로 다른 페이지나 유튜브 영상을 끼워 넣는 것까지 다뤘다.

<form action="11_form.html" method="post"> <label for="username">아이디</label> <input type="text" id="username" name="_username"> <input type="submit" value="로그인"> </form>

폼에서 가장 중요하게 짚은 건 두 가지였다. get은 입력값을 URL 뒤 쿼리스트링으로, post는 요청 본문에 담아 보낸다는 것, 그리고 서버로 넘어가는 키는 id가 아니라 name 속성이라는 것이다. email, url, tel 같은 input 타입은 형식 검사나 숫자 키패드를 브라우저가 알아서 붙여준다. 반복 작성은 Emmet 약어(ul>li*3, p.para>lorem)로 줄였다.

06. CSS 선택자와 우선순위

CSS는 "어떤 요소를 골라서 어떻게 꾸밀지"를 적는다. 그래서 고르는 방법, 즉 선택자부터 정리했다.

ul { } /* 태그 */ #foo1 { } /* 아이디 */ .group1.group2 { } /* 두 클래스를 모두 가진 요소 */ [title=안녕2] { } /* 속성 */ #parent > h4 { } /* 바로 아래 자식 */ #parent h4 { } /* 모든 후손 */ #p1 + p { } /* 바로 다음 형제 하나 */

같은 요소에 규칙이 겹치면 더 구체적인 선택자가 이긴다. 아이디 > 클래스·속성 > 태그 순으로 점수를 매겨 비교하는 방식이었다. 예제에서 div.foo[title=box]는 태그 1개, 클래스 1개, 속성 1개라 .foo보다 점수가 높은데, .foo에 !important를 붙이자 점수와 상관없이 .foo가 이겼다. 강력하지만 한 번 쓰면 뒤에서 덮어쓰기가 어려워지니 되도록 피하라는 이야기도 같이 들었다.

07. 글자와 박스 — 폰트·단위·박스 모델

폰트는 font-family에 여러 개를 나열하면 왼쪽부터 있는 걸 쓰고, 마지막에 sans-serif 같은 일반 계열을 적어 안전장치로 둔다. 여러 속성은 font: italic bold 48px/48px 'Dongle', sans-serif처럼 한 줄로 모아 쓸 수 있다. 크기 단위는 네 가지를 비교했다.

#parent :first-child { font-size: 24px; } /* 고정 */ #parent :nth-child(2) { font-size: 150%; } /* 부모 기준 */ #parent :nth-child(3) { font-size: 1.5em; } /* 부모 기준 */ #parent :last-child { font-size: 1.5rem; } /* 루트(html) 기준 */

부모 글자 크기를 32px, html을 50px로 두니 em과 rem의 차이가 확실히 보였다. 박스 모델은 content → padding → border → margin 순으로 바깥으로 쌓이고, padding: 10px 20px처럼 값을 생략하면 맞은편 값을 따라간다. 여기서 헷갈렸던 건 span 같은 inline 요소에는 width/height와 위아래 margin이 적용되지 않는다는 점이었다.

요소를 안 보이게 하는 방법도 세 가지가 달랐다. display: none은 자리까지 없어지고, visibility: hidden과 opacity: 0은 안 보여도 자리는 그대로 남는다. 그 밖에 border-radius: 50%로 원 만들기, text-shadow를 여러 겹 쌓아 불꽃 글씨 만들기 같은 꾸미기도 해봤다.

08. 배치 — position, flexbox, grid, 시멘틱 레이아웃

position은 기준점이 핵심이었다. relative는 원래 자리 기준, absolute는 가장 가까운 position 조상 기준, fixed는 화면 기준, sticky는 스크롤하다 지정 위치에서 붙는다. 겹칠 때 앞뒤는 z-index가 클수록 앞이다.

.container { display: flex; flex-wrap: wrap; /* 넘치면 줄 바꿈 */ gap: 16px; justify-content: space-between; /* 주 축 정렬 */ align-items: center; /* 교차 축 정렬 */ } .item.order-first { order: -1; } /* 작성 순서와 상관없이 맨 앞으로 */

flexbox는 한 방향으로 늘어놓는 배치다. flex: 1 1 120px처럼 기준 크기를 정하고 남거나 모자란 공간을 비율로 나눠 갖게 할 수 있다. 수평·수직 가운데 정렬도 justify-content와 align-items 두 줄이면 끝났다.

.container3 { display: grid; grid-template-rows: 1fr 1fr 1fr; grid-auto-flow: column; /* 셀을 세로 방향으로 채움 */ } .item01 { grid-row: 1/4; } /* 1번 줄부터 4번 줄 앞까지 = 3칸 */ .item02 { grid-column: 2/4; }

grid는 행과 열을 동시에 다루는 배치다. 칸을 나눈 뒤 grid-row, grid-column으로 요소가 몇 칸을 차지할지 정한다. 숫자가 칸 번호가 아니라 선 번호라서 1/4가 세 칸이라는 게 처음엔 헷갈렸다. 마지막으로 header, nav, main, section, aside, footer 같은 시멘틱 태그로 뼈대를 잡고, flex로 본문과 사이드바를 나란히 놓는 전형적인 페이지 레이아웃을 만들어봤다.

KPT 회고

Keep

이슈 → 브랜치 → 커밋 → PR → 머지를 실제 저장소에서 한 바퀴 돌려봤다. 설명으로만 들으면 번거로운 절차처럼 느껴졌을 텐데, 로그 그래프에 흐름이 그대로 남는 걸 보고 나니 왜 이렇게 하는지 납득이 됐다. CI도 지난주 만든 Iris API를 그대로 이어 쓰면서 붙였기 때문에, 새로 배운 부분에만 집중할 수 있었다.

Problem

HTML과 CSS는 속성 수가 워낙 많아서, 하나씩 이해하기보다는 브라우저에서 결과를 확인하고 넘어가는 식이 됐다. 선택자나 position처럼 원리가 있는 건 정리가 됐지만, 폰트·텍스트 쪽은 머리에 남은 게 적다. 그리고 지금 CI는 모델을 DVC로 관리하면서도 정작 파이프라인에서는 매번 새로 학습하고 있다. 지난주 Try였던 이미지 모델 서빙과 동영상 RAG도 이번 주 진도에 밀려 손을 못 댔다.

Try

DVC에 원격 저장소를 연결해서 CI가 모델을 새로 학습하는 대신 dvc pull로 받아오게 바꿔보려 한다. HTML·CSS는 속성을 외우기보다 블로그 같은 실제 페이지 하나를 골라 레이아웃을 직접 따라 짜보면서 익힐 생각이다.

새롭게 발견한 것

CI가 train.py부터 돌리는 데는 이유가 있었다. 처음엔 테스트 전에 왜 학습을 하는지 의아했는데, DVC와 연결해서 보니 이해가 됐다. .gitignore가 model/*.joblib을 빼고 있으니 GitHub 러너가 checkout한 코드에는 모델 파일이 없고, .dvc/config에 원격 저장소도 설정돼 있지 않으니 받아올 곳도 없다. 그런데 app/main.py는 import되는 순간 모델을 로드하기 때문에, 학습을 먼저 안 하면 테스트가 시작도 못 한다. 따로 배운 세 가지가 한 파일 안에서 서로 맞물려 있었다.

URL로 페이지 속 문장을 가리킬 수 있다. 앵커 링크는 id가 있어야만 되는 줄 알았는데, #:~:text=찾을 문장처럼 쓰면 브라우저가 해당 문장까지 스크롤하고 하이라이트까지 해준다. 검색 결과에서 눌렀을 때 문장이 노랗게 칠해져 있던 게 이 기능이었다.

블로그 코드가 다르게 보인다. 이 회고를 올리는 블로그도 결국 HTML과 CSS다. 이번 주에 배운 걸 들고 style.css를 다시 열어보니, 그냥 복사해 쓰던 :root 변수, :not(.code-block) > code 같은 선택자, flex 배치가 무슨 뜻인지 읽혔다.

문제 : 내비게이션 링크를 눌러도 해당 섹션으로 이동하지 않았다

샘플 페이지에 Section1~Section3 링크를 만들었는데, 클릭하면 주소창에 #section1만 붙고 화면은 그대로였다.

<a href="#section1">Section1</a> ... <section id="#section1" class="'section-content">

원인은 속성값이었다. 링크의 #은 "이 id로 가라"는 표시일 뿐인데, id 값 자체에도 #을 넣어버려서 실제 id가 #section1이 돼 있었다. 그러니 section1이라는 id를 찾는 링크와 맞을 리가 없었다. 같은 파일에서 class="'section-content", href="'https://naver.com"처럼 따옴표가 값 안에 한 번 더 들어간 곳도 여럿 보였다. 에디터 자동완성으로 따옴표가 두 번 들어간 걸 못 본 것이다.

<section id="section1" class="section-content">

id는 # 없이, 따옴표는 한 겹만 쓰니 링크가 제대로 동작했다. HTML은 틀린 값을 넣어도 에러를 내지 않고 조용히 무시하기 때문에, 화면이 이상할 때는 개발자 도구로 실제 속성값부터 확인하는 게 빠르다는 걸 배웠다.

문제 : Windows에서 뽑은 requirements.txt를 Ubuntu 러너에 그대로 쓸 수 없었다

로컬(Windows)에서 pip freeze로 뽑은 requirements.txt에는 pywin32가 들어 있었다. Windows 전용 패키지라 리눅스인 GitHub Actions 러너에서는 설치할 수 없다.

pywin32==312

이걸 지우면 로컬 환경이 깨지니, 대신 환경 마커를 붙여 "Windows일 때만 설치"하도록 조건을 달았다. 그런데 다시 보니 조건 문자열에 오타가 있었다.

pywin32==312; platform_system == "Windowns" # 수정 전 — 어떤 OS에서도 거짓 pywin32==312; platform_system == "Windows" # 수정 후

러너에서는 어차피 조건이 거짓이어야 하니 CI만 보면 오타가 드러나지 않는다. 대신 Windows에서 새로 환경을 만들면 pywin32가 빠진다. 통과했다고 해서 설정이 맞다는 보장은 없다는 것, 그리고 운영체제마다 다른 패키지는 platform_system 같은 마커로 나눠 적는다는 걸 같이 정리했다.
