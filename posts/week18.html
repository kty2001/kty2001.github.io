이번 주 학습 내용

지난주에는 Django를 EC2에 runserver로 띄우는 데서 끝났고, 다음 단계로 gunicorn을 Try에 적어뒀다. 이번 주 수업이 마침 그 자리에서 이어졌다. 먼저 컨테이너 여러 개를 Docker Compose 파일 하나로 묶는 법을 배우고, 같은 방식으로 Django를 gunicorn과 PostgreSQL 컨테이너로 다시 구성했다. 이어서 서버를 띄워두지 않고 함수 하나만 올려두는 AWS Lambda를 써봤다. 주 후반은 4차 팀 프로젝트 발표와 마무리였다.

01. Docker Compose — 컨테이너 두 개를 파일 하나로

Week 14에서는 FastAPI 앱 하나를 이미지로 만들어 컨테이너 하나로 띄웠다. 이번에는 FastAPI 앱과 MySQL을 같이 띄웠다. 컨테이너가 두 개가 되면 docker run을 따로 두 번 치고, 네트워크와 환경변수를 매번 맞춰줘야 한다. 이걸 파일 하나에 적어두고 한 번에 올리는 게 Docker Compose다.

services: app: build: context: . dockerfile: Dockerfile ports: - "60080:8000" # 호스트 60080 → 컨테이너 8000 depends_on: - mysql environment: - DB_HOST=mysql # localhost가 아니라 서비스 이름 - DB_PORT=3306 - DB_NAME=cloud_db restart: always mysql: image: mysql:8.0 volumes: - ./mysqldata:/var/lib/mysql # 컨테이너를 지워도 데이터는 남는다 environment: - MYSQL_DATABASE=cloud_db ports: - "63306:3306"

제일 먼저 눈에 들어온 건 DB_HOST=mysql이었다. Compose로 띄운 컨테이너들은 같은 네트워크에 묶이고, 서비스 이름이 그대로 주소가 된다. 컨테이너 안에서 localhost는 그 컨테이너 자기 자신이라, 앱 컨테이너에서 localhost:3306으로 접속하면 MySQL을 찾지 못한다.

ports는 호스트:컨테이너 순서다. 내 PC에서는 60080으로 들어가고, 컨테이너 안의 uvicorn은 원래대로 8000에서 받는다. volumes는 MySQL 데이터 폴더를 내 PC의 ./mysqldata와 연결해서, 컨테이너를 지웠다가 다시 올려도 테이블이 그대로 남게 한다. depends_on은 MySQL 컨테이너를 먼저 시작하게 해주지만, MySQL이 접속을 받을 준비가 됐는지까지 기다려주지는 않는다고 한다. 실습에서는 DB 비밀번호를 compose 파일에 그대로 적었는데, 다음 실습에서 이 값을 .env로 빼는 방법이 나왔다.

02. Django를 컨테이너로 — runserver 대신 gunicorn, SQLite 대신 PostgreSQL

지난주 EC2에 올렸던 그 Django 페이지를 이번에는 컨테이너로 다시 구성했다. 바뀐 건 두 가지다. 개발용 runserver 대신 gunicorn으로 실행하고, SQLite 파일 대신 PostgreSQL 컨테이너를 DB로 쓴다.

FROM python:3.12-slim ENV PYTHONDONTWRITEBYTECODE 1 # .pyc 파일을 만들지 않음 ENV PYTHONUNBUFFERED 1 # print·로그를 바로 출력 → docker logs에 즉시 보임 WORKDIR /app COPY requirements.txt . RUN pip install --upgrade pip RUN pip install -r requirements.txt COPY . . RUN mkdir -p /app/staticfiles EXPOSE 8000 CMD ["gunicorn", "--bind", "0.0.0.0:8000", "django_web.wsgi"]

runserver는 개발할 때 편하라고 만든 서버라 실제 서비스용이 아니다. gunicorn은 wsgi.py의 application을 받아 실행하는 WSGI 서버라서, 마지막 줄의 django_web.wsgi가 프로젝트 이름에 맞아야 한다. 환경변수 두 줄도 컨테이너라서 필요한 설정이었다. 특히 PYTHONUNBUFFERED가 없으면 출력이 버퍼에 쌓여 있다가 늦게 나와서, docker logs로 로그를 볼 때 답답해진다.

services: web: build: . command: gunicorn django_web.wsgi:application --bind 0.0.0.0:8000 ports: - "8001:8000" env_file: - .env # 비밀번호는 여기서만 읽는다 depends_on: - db db: image: postgres:15 volumes: - postgres_data:/var/lib/postgresql/data environment: - POSTGRES_DB=${POSTGRES_DB} - POSTGRES_USER=${POSTGRES_USER} - POSTGRES_PASSWORD=${POSTGRES_PASSWORD} volumes: postgres_data:
# settings.py DATABASES = { 'default': { 'ENGINE': 'django.db.backends.postgresql', 'NAME': os.environ.get('POSTGRES_DB'), 'USER': os.environ.get('POSTGRES_USER'), 'PASSWORD': os.environ.get('POSTGRES_PASSWORD'), 'HOST': 'db', # compose의 서비스 이름 'PORT': '5432', } }

01과 비교하면 비밀번호가 compose 파일에서 사라지고 ${POSTGRES_PASSWORD} 같은 자리표시자만 남았다. 실제 값은 .env에 있고, .dockerignore에도 .env를 넣어서 이미지 안에는 들어가지 않는다. 비밀번호는 이미지를 만들 때가 아니라 컨테이너를 실행할 때 넣어주는 셈이다. 볼륨도 01의 ./mysqldata 같은 폴더 경로 대신 postgres_data라는 이름만 붙인 볼륨을 썼고, 이 볼륨은 Docker가 알아서 관리한다.

settings.py의 STATIC_ROOT에는 "배포 시 gunicorn과 사용할 정적 파일 저장 위치"라는 주석이 붙어 있었다. gunicorn은 runserver처럼 CSS·JS를 알아서 내려주지 않기 때문에, collectstatic으로 파일을 한곳에 모으고 nginx 같은 웹 서버가 그 폴더를 서빙하는 구성이 보통이라고 한다. 이번 실습은 Dockerfile에서 폴더를 만들어두는 데까지였고, nginx는 아직 붙이지 않았다.

03. AWS Lambda — 서버 없이 함수 하나만

EC2는 서버를 하나 빌려서 계속 켜두는 방식이었다. Lambda는 반대로 함수 하나만 올려두고, 요청이 들어올 때만 실행된다. 서버를 띄우거나 관리할 필요가 없고, 실행된 만큼만 요금이 나온다. 함수 이름은 lambda_handler(event, context)로 정해져 있고, 들어온 요청은 event에 담겨 온다.

import json def lambda_handler(event, context): try: if "body" not in event: # 콘솔 테스트: 입력한 dict가 그대로 event name = event.get("name", "World") else: # API Gateway: 요청 본문이 JSON '문자열'로 body에 들어옴 body = json.loads(event.get("body", "{}")) name = body.get("name", "World") return { "statusCode": 200, "headers": {"Content-Type": "application/json"}, "body": json.dumps({"message": f"Hello, {name}!"}, ensure_ascii=False) } except Exception as e: return {"statusCode": 500, "body": json.dumps({"error": str(e)}, ensure_ascii=False)}

같은 함수인데 event의 모양이 누가 부르느냐에 따라 달랐다. Lambda 콘솔의 테스트 버튼으로 실행하면 입력한 JSON이 그대로 event가 된다. 반면 API Gateway를 거쳐 HTTP로 부르면 요청 전체가 감싸져서 들어오고, 본문은 event['body']에 문자열로 들어 있다. 그래서 body 키가 있는지로 두 경우를 나눴다. 돌려줄 때도 statusCode, headers, body 형식을 맞춰야 API Gateway가 HTTP 응답으로 바꿔준다. 한글 메시지가 깨지지 않게 ensure_ascii=False도 붙였다. 코드는 콘솔에서 바로 쓰는 방법 말고 ZIP으로 묶어 올리는 방법도 해봤다.

마지막으로 Django에서 이 Lambda를 불렀다. 텍스트 요약 Lambda를 API Gateway 주소로 열어두고, Django view는 받은 텍스트를 그 주소로 넘기기만 한다.

@csrf_exempt def summarize_view(request): if request.method == "POST": user_input = json.loads(request.body).get("text", "") lambda_url = "https://<API_ID>.execute-api.<REGION>.amazonaws.com/<STAGE>" try: response = requests.post(lambda_url, json={"text": user_input}, headers={"Content-Type": "application/json"}) return JsonResponse({"summary": response.json().get("summary", "")}) except Exception as e: return JsonResponse({"error": str(e)}, status=500) return JsonResponse({"error": "POST only"}, status=405)

지난주 Django + FastAPI 챗봇과 구조가 거의 같다. Django가 requests.post()로 다른 곳에 일을 넘기고 결과만 돌려준다. 차이는 받는 쪽이다. 지난주에는 8001번 FastAPI 서버를 터미널에 계속 띄워둬야 했는데, 이번에는 띄워둘 서버가 없다. 요청이 올 때만 Lambda가 실행되고 끝나면 내려간다. 지난주에 "FastAPI를 안 켜두면 연결 오류가 난다"고 적었던 불편함이 이 구조에서는 생기지 않는다.

KPT 회고

Keep

지난주 Try에 적었던 gunicorn을 이번 주에 바로 컨테이너 안에서 써봤다. 수업과 프로젝트가 맞물린 것도 좋았다. 수업에서 compose를 배우는 동안 프로젝트에서는 이미 compose 파일 네 개(로컬·개발·App EC2·Data EC2)로 서비스를 운영하고 있었다. 그래서 서비스 이름이 주소가 된다는 것이나 env_file로 비밀값을 넣는 이유가 설명만 듣고 끝나지 않고, 우리 프로젝트 구성을 다시 이해하는 데로 이어졌다. 4차 프로젝트도 발표까지 마무리했다.

Problem

nginx와 collectstatic은 이번에도 설명으로만 들었다. Lambda는 Hello World 함수와 호출까지만 해봤고, 콘솔에서 API Gateway를 연결하고 권한을 설정한 과정은 따로 정리하지 않으면 다시 하기 어려울 것 같다. 프로젝트 쪽은 운영 문제 대부분이 배포한 뒤 점검하면서 드러났다. 미리 막은 것보다 터진 뒤에 고친 게 많았고, 목표 아키텍처는 문서로만 남기고 구현까지는 가지 못했다.

Try

수업 compose 예제에 nginx 서비스를 하나 추가해서 정적 파일 서빙과 프록시를 직접 붙여볼 생각이다. Lambda는 요약 함수를 직접 만들어 API Gateway에 연결하고, 환경변수와 실행 제한 시간을 어디서 설정하는지 순서대로 적어두려 한다. 프로젝트 개선안에서 제일 작게 시작할 수 있는 "jobs 테이블로 오래 걸리는 작업을 비동기로 돌리기"도 작은 예제로 만들어볼 생각이다.

새롭게 발견한 것

컨테이너 안의 localhost는 자기 자신이다. 내 PC에서는 앱과 DB가 같은 컴퓨터에 있으니 localhost로 붙었지만, 컨테이너로 나누면 각자가 별개의 컴퓨터처럼 동작한다. 그래서 Compose에서는 mysql, db 같은 서비스 이름으로 서로를 찾는다. 프로젝트 compose의 DB 접속 주소가 왜 localhost가 아니라 db였는지 이제야 이해됐다.

폴더 볼륨은 진짜 내 폴더에 쌓인다. 01 실습이 끝나고 로컬 실습 폴더를 보니 mysqldata가 200MB 넘게 커져 있었다. ./mysqldata처럼 경로로 연결한 볼륨은 MySQL 데이터 파일이 내 프로젝트 폴더에 그대로 생겨서, .gitignore에 넣지 않으면 git에 같이 올라갈 뻔한다. 02처럼 이름만 붙인 볼륨은 Docker가 따로 관리해서 프로젝트 폴더에는 보이지 않는다.

Lambda의 event는 부르는 쪽이 정한다. 함수 코드는 하나인데, 콘솔 테스트에서는 dict가 그대로 오고 API Gateway에서는 본문이 문자열로 한 번 감싸져서 온다. 처음에 콘솔에서만 테스트하고 넘어갔다면 HTTP로 불렀을 때 json.loads가 빠져서 바로 막혔을 것 같다.

트러블슈팅

문제 : 화면에는 실패가 뜨는데 서버는 LLM을 계속 부르고 있었다

4차 프로젝트를 AWS에 배포한 뒤 점검하다가 발견한 문제다. 사업계획서 AI 진단 버튼을 누르면 한참 뒤 화면에 실패 메시지가 뜨는데, 서버 로그를 보면 LLM 호출이 끝까지 진행되고 있었다. 사용자가 실패를 보고 다시 누르면 같은 요청이 한 번 더 LLM으로 가서 비용이 두 배로 나간다.

원인은 제한 시간이 서로 맞지 않는 데 있었다. 프런트는 70초까지만 기다리고 포기하는데, Backend는 LLM 응답을 최대 120초까지 기다린다. 개발 PC에서는 대부분 70초 안에 끝나서 드러나지 않았고, 상대적으로 느린 EC2에서 이 구간에 걸리는 경우가 늘어났다.

// 수정 전 — 프런트(70초)가 Backend → LLM(120초)보다 먼저 포기 evaluateBusinessPlan: (body, opt) => apiPost('/bizplan/evaluate', body, { timeout: 70000, ...opt }), // 수정 후 — 프런트 제한 = Backend → LLM 제한 + 10초 이상 // 프런트가 먼저 포기하면 서버는 작업을 끝내고도 실패로 보이고, 재시도로 LLM 호출이 중복된다. evaluateBusinessPlan: (body, opt) => apiPost('/bizplan/evaluate', body, { timeout: 130000, ...opt }),

"프런트 제한 시간은 Backend가 LLM을 기다리는 시간보다 10초 이상 길게"를 원칙으로 정하고, LLM을 부르는 호출을 전부 다시 맞췄다. 사업계획서 진단·정리·출력은 70초에서 130초로, 공고 요약은 30초에서 60초로, 창업 감면 확인은 30초에서 45초로 늘렸다. 원래 영수증 OCR 쪽 설정에만 같은 경고 주석이 있었고 다른 기능에는 적용되지 않은 상태였다. 요청이 여러 단계를 거칠 때는 바깥쪽이 안쪽보다 오래 기다려야 한다는 걸, 값 하나씩 표로 나란히 놓고 보면서 알게 됐다.

프로젝트 진행 과정

3차 프로젝트 "창업ON"을 그대로 이어받아 4차에서 고도화했다. 9월 18일에 3차 코드를 새 저장소로 옮기며 시작했고, 10월 14일에 발표를 마쳤다. 3차가 "질문에 근거 있게 답하는 것"에 집중했다면, 4차는 기능을 넓히고 실제로 배포해서 운영하는 것에 가까웠다. 팀에서는 PM과 Backend·DevOps를 맡았다.

  • Backend를 Django로 — 수업에서 Django를 배우던 시기에 맞춰 FastAPI Backend를 Django + Django Ninja로 옮겼다. 라우터를 add_router()로 기능별로 나누는 구조라 옮기는 부담이 크지 않았다. 남아 있던 SQLite와 브라우저 localStorage 저장도 걷어내고, 사용자 데이터를 PostgreSQL 한곳에 모았다
  • 기능 확장 — 영수증 사진을 올리면 OCR로 읽고, 9개 지출 항목으로 분류한 뒤, 적격증빙 규칙과 세법 검색을 묶어 경비처리를 "인정 / 확인 필요 / 불인정"으로 판정하는 지출관리를 붙였다. 아이디어를 넣으면 공고 양식에 맞춘 사업계획서 초안을 쓰고 0~100점으로 예비진단하는 기능, PWA·HTTPS와 모바일 화면도 이번에 추가됐다
  • 해보고 결정한 것 — OCR은 무료 엔진 네 가지를 비교해 Tesseract에서 PP-OCRv5 한국어로 바꿨다. 영수증 5장 기준 정확도 82%에서 97%, 처리 시간 25.9초에서 12.1초로 좋아졌다. 반대로 Elasticsearch Nori 검색기는 이전 데이터에서 정책 Hit@5가 84.1%에서 92.1%로 올랐지만, 근거 데이터를 늘린 뒤 다시 재보니 기본 BM25와 차이가 없어서 운영에서는 빼고 코드만 남겼다. 근거 판정 LLM을 CatBoost로 바꾸는 실험도 통과율이 77.8%에서 22.2%로 떨어져 채택하지 않았다
  • AWS 배포와 자동화 — 사용자가 접속하는 App EC2(public, nginx·HTTPS)와 DB만 두는 Data EC2(private)로 나눴다. GitHub Actions에서 이미지를 빌드해 레지스트리에 올리고 EC2는 받아서 띄우기만 한다. 워크플로는 배포, 주 1회 데이터 수집, 실패한 수집의 3시간 간격 재시도, 6시간 간격 상태 점검 네 개였고, DB는 매일 S3로 백업하고 실패하면 알림이 오게 했다
  • 배포 후 점검 — 배포를 마친 뒤 위험 보고서를 따로 만들어 문제를 번호별로 정리하고 하나씩 고쳤다. 같은 그룹에 묶인 워크플로끼리 서로 취소되던 문제는 배포에만 대기열과 서버 잠금을 걸어 순서대로 돌게 했다. EC2에서 이미지 빌드와 워밍업이 겹쳐 메모리가 부족하던 문제는 빌드를 Actions로 옮겨 해결했다. 이 밖에 재색인 동안 검색이 전부 멈추던 것, 백업 cron이 PATH 문제로 아무 메시지 없이 실패하던 것, 컨테이너 시간대가 UTC라 마감 D-day가 하루씩 어긋나던 것도 이때 잡았다
  • 이번 주 — 화면 설계서와 목표 아키텍처 개선안을 정리하고, README와 발표 자료를 마무리했다. 개선안의 핵심은 LLM 컨테이너 하나가 상담·OCR·문서 출력·재색인을 전부 하던 구조를 나누는 것이다. 상담만 바로 응답하고, OCR이나 사업계획서처럼 오래 걸리는 작업은 작업 ID를 먼저 돌려준 뒤 큐에 쌓아 별도 워커가 처리하는 방식이다

개선안을 쓰던 주에 Lambda를 배운 게 공교로웠다. 필요할 때만 실행되는 작은 작업 단위로 나누면 서로의 부하가 번지지 않는다는 생각이, 개선안에서 워커를 분리하려던 이유와 같은 방향이었다. 프로젝트 한 줄 회고에는 "CI/CD, 스케줄링, PWA, AWS처럼 써보고 싶던 기술을 모두 도입해볼 수 있어서 좋았다"고 적었다.
