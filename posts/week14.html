이미지와 텍스트가 같은 공간에서 만나다 — 멀티모달, 그리고 모델을 서비스로

이번 주 학습 내용

지난주에 "모델이 이미지를 어떻게 보는가"까지 정리했다면, 이번 주는 그 이미지를 텍스트와 어떻게 연결하는가로 넘어갔다. 이미지와 문장을 같은 공간에 놓는 CLIP에서 출발해, 설명을 만들어내는 BLIP, 이미지를 읽고 대답하는 LLM, 반대로 문장에서 그림을 만드는 생성 모델, 그리고 그걸 검색에 얹은 멀티모달 RAG까지 이어졌다. 주 후반에는 결이 전혀 다른 수업으로, 학습한 모델을 API로 띄우고 컨테이너에 담는 과정을 따라갔다. 같은 주에 3차 팀 프로젝트 발표까지 있어서 마무리와 새 진도가 겹친 한 주였다.

01. CLIP — 이미지와 텍스트를 같은 공간에

CLIP은 이미지 인코더와 텍스트 인코더를 따로 두되, 둘의 출력이 같은 임베딩 공간에 떨어지도록 학습된 모델이다. 학습 자체는 "짝이 맞는 이미지-문장 쌍은 가깝게, 아닌 쌍은 멀게" 당기는 방식이다. 설명만 들었을 땐 감이 안 왔는데, 실제로 벡터를 뽑아보니 구조가 단순했다.

model = CLIPModel.from_pretrained('openai/clip-vit-base-patch32') image_embeds = model.get_image_features(pixel_values=pixel_values) # 이미지 → 벡터 text_embeds = model.get_text_features(input_ids=input_ids, ...) # 문장 → 벡터 cosine_similarity(image_embeds, text_embeds) # 같은 공간이니 그냥 코사인 유사도

골든 리트리버 사진 한 장과 'a photo of a cat', 'a photo of a dog', 'a landscape with mountains' 세 문장을 각각 벡터로 바꾸고 코사인 유사도만 계산했더니 개 쪽이 가장 높게 나왔다. 학습할 때 본 적 없는 라벨이라도 문장으로 써주기만 하면 분류가 되는 제로샷 분류가, 결국 유사도 비교 한 줄이었다는 게 인상적이었다. 대신 비슷한 품종을 구별하거나 개수를 세는 것처럼 세밀한 판단에는 약하다는 한계도 같이 짚고 넘어갔다.

02. BLIP — 이해에 생성을 더하다

CLIP이 이미지와 텍스트를 맞춰보는 데까지였다면, BLIP은 거기에 만들어내는 기능이 붙는다. 인코더와 디코더를 섞은 구조라 같은 모델 계열로 캡셔닝, 이미지-텍스트 매칭, 시각 질의응답을 모두 할 수 있었다. 해변에서 강아지와 앉아 있는 데모 사진 한 장으로 세 가지를 차례로 돌려봤다.

# 캡셔닝 — 접두어를 주면 그 뒤를 이어서 쓴다 inputs = processor(raw_image, 'a photography of', return_tensors='pt') processor.decode(model.generate(**inputs)[0], skip_special_tokens=True) # ITM — 문장이 이미지와 맞는지 점수로 판정 itm_scores = model(**inputs)[0] print('Matched' if itm_scores.argmax(dim=-1) else 'Not Matched')

캡셔닝은 접두어를 주면 그 문장을 이어서 완성했고, 아무것도 주지 않으면 알아서 처음부터 문장을 만들었다. 매칭 모델에는 "여자와 개가 해변에 함께 앉아 있다"와 "여자와 개가 서로 적대적이다" 두 문장을 넣어봤는데, 같은 사진인데도 앞쪽만 Matched로 나왔다. 질의응답 모델까지 돌려보고 나니 정렬만 하는 모델과 생성까지 하는 모델의 차이가 확실히 구분됐다.

03. Llama 3.2 Vision — 이미지를 읽는 LLM

여기서부터는 이미지 전용 모델이 아니라, LLM이 이미지를 같이 받는 쪽이었다. 이미지를 비전 인코더로 벡터로 바꿔 텍스트 토큰과 함께 넣어주면, 그다음부터는 평소 쓰던 대화 형식 그대로 흘러간다. 메시지에 {'type': 'image'} 한 칸이 추가된 게 거의 전부였다.

messages = [{'role': 'user', 'content': [ {'type': 'image'}, {'type': 'text', 'text': question} ]}] input_text = processor.apply_chat_template(messages, add_generation_prompt=True) inputs = processor(image, input_text, add_special_tokens=False, return_tensors='pt') # pixel_values: (1, 1, 4, 3, 560, 560) → (배치, 이미지 수, 타일 수, 채널, 높이, 너비)

한국어 음식 VQA 데이터셋으로 실제 정답과 비교해봤다. 이미지 정보, 질문, 정답이 각각 다른 JSON 파일에 나뉘어 있어서 파일명으로 image_id를 찾고, 그 id로 질문들을 모으고, 다시 question_id로 정답을 찾아오는 헬퍼 함수를 만들어 이어 붙였다. 모델을 돌리는 코드보다 데이터를 짝지어주는 코드가 더 길었는데, 오히려 그 과정에서 VQA 데이터가 어떤 모양인지 더 잘 이해됐다.

pixel_values의 shape을 찍어보니 타일 개수 축이 따로 있었다. 큰 이미지를 여러 조각으로 잘라 넣고, cross_attention_mask로 어떤 텍스트 토큰이 어떤 타일을 참조할지 표시하는 구조였다. 마지막으로는 통계 그래프 이미지 한 장을 넣고 제목·축·수치·색까지 빠짐없이 설명하게 하는 긴 캡셔닝 프롬프트를 돌려봤는데, 막연히 "설명해줘"라고 할 때와 항목을 나눠 지시할 때의 결과 차이가 텍스트 프롬프트에서와 똑같이 나타났다.

04. 이미지 생성 — 문장에서 그림으로

방향을 뒤집어 텍스트에서 이미지를 만드는 쪽도 다뤘다. Stable Diffusion은 이미지를 직접 다루지 않고, 저차원 잠재 공간으로 압축한 뒤 그 안에서 노이즈를 걷어내는 방식으로 그림을 만든다. 연산량이 크게 줄어드는 이유가 여기 있었다. Week 10에서 파이프라인을 한 번 돌려보기만 했었는데, 이번엔 손잡이가 뭐가 있는지까지 봤다.

set_seed(100) # 같은 시드 → 같은 출발 노이즈 result = pipe( 'A serene landscape of mountains during sunrise, minimalist', num_inference_steps=50, # 노이즈를 몇 번에 걸쳐 걷어낼지 guidance_scale=7.5 # 프롬프트를 얼마나 강하게 따를지 )

시드를 고정해두고 프롬프트 끝의 스타일 키워드만 minimalist → impressionist → anime style로 바꿔가며 같은 풍경을 뽑아봤다. 구도는 비슷하게 유지되는데 질감과 색감만 통째로 갈아입는 게 재밌었다. 프롬프트 한 단어가 결과를 얼마나 크게 흔드는지 눈으로 확인한 셈이다.

OpenAI의 이미지 생성 API도 써봤다. 이쪽은 응답에서 base64 문자열을 꺼내 파일로 디코딩해 저장하는 방식이라, 모델을 직접 띄울 필요 없이 몇 줄로 끝났다. 직접 돌리는 쪽은 시드와 스텝까지 만질 수 있고 API 쪽은 간편한 대신 통제할 수 있는 게 적다는, 익숙한 트레이드오프가 이미지에서도 똑같이 보였다.

05. 멀티모달 RAG — 이미지를 캡션으로 바꿔 검색하기

그동안 RAG는 전부 텍스트 문서를 대상으로 했는데, 이번엔 이미지가 자료인 경우를 다뤘다. 방법은 생각보다 단순했다. 이미지를 모델에 넣어 설명을 받아내고, 그 설명을 문서처럼 벡터 DB에 넣는다. 검색은 평소처럼 텍스트끼리 하고, 답변할 때 원본 이미지를 다시 꺼내 보여주면 된다.

for img_path in tqdm(image_files): caption = summarize_image(img_path) # 이미지 → 설명 텍스트 vector_db.add_texts( texts=[caption], metadatas=[{'base64_image': image_to_base64(img_path), # 원본을 같이 보관 'image_path': img_path}] )

핵심은 metadatas에 원본 이미지를 base64로 함께 저장해둔 부분이었다. 검색은 캡션으로 하지만, 꺼낼 땐 그 캡션에 딸린 그림을 같이 돌려줄 수 있다. 소방 안전교육 자료 이미지들을 넣어두고 "완강기는 어떻게 써야 하나"라고 물으니, 관련 캡션 두 건과 해당 그림이 함께 나왔다.

답변 생성은 에이전트에 미들웨어를 끼우는 방식으로 붙였다. Week 11에서 봤던 그 미들웨어인데, 이번엔 before_model에서 마지막 사용자 메시지로 검색을 돌리고 그 결과를 프롬프트에 끼워 넣는 용도로 썼다. 체인을 따로 짜지 않고 "모델 호출 직전에 문서를 주입한다"는 한 지점만 건드리면 되는 게 깔끔했다.

06. 동영상 RAG 준비 — 프레임 추출과 장면 해설

이미지가 됐으면 영상도 된다. 영상은 결국 프레임의 연속이니, 일정 간격으로 프레임을 뽑아 각각을 이미지로 취급하면 앞의 방식을 그대로 쓸 수 있다는 흐름이었다. 먼저 OpenCV 기초를 짚었다. NumPy 배열로 단색 이미지를 만들어 저장해보고, VideoCapture로 영상을 열어 프레임 수와 FPS로 길이를 계산하고, 첫 프레임을 썸네일로 줄여 미리보기를 만드는 식이었다.

cap = cv2.VideoCapture(video_path) frame_count = int(cap.get(cv2.CAP_PROP_FRAME_COUNT)) while True: ret, frame = cap.read() if not ret: break if idx % frame_interval == 0: # 30프레임마다 한 장 cv2.imwrite(f'{save_subdir}/{video_name}_frame{idx:05d}.jpg', frame) idx += 1

스키 영상을 30프레임 간격으로 잘라 영상별 폴더에 저장하고, 그 프레임들을 하나씩 모델에 넣어 "장면 해설가" 역할을 준 프롬프트로 짧은 설명을 받아 캡션 파일로 모았다. 여기까지는 돌아갔는데, 그 캡션을 벡터 DB에 넣고 실제로 영상에 질문해보는 단계까지는 가지 못하고 주가 끝났다. 재료만 만들어두고 요리를 안 한 셈이라 아쉬움이 남았다.

07. 모델을 서비스로 — FastAPI와 Docker

주 후반에는 방향이 완전히 달라졌다. 지금까지는 노트북 안에서 모델을 돌리고 결과를 출력하는 게 끝이었는데, 이번엔 그걸 남이 쓸 수 있는 형태로 내보내는 과정을 따라갔다. 순서는 학습 → 저장 → API → 컨테이너였다.

먼저 학습 코드와 서빙 코드를 분리했다. train.py는 Iris 데이터로 랜덤 포레스트를 학습한 뒤 모델과 클래스 이름을 함께 joblib 파일로 저장하고 끝난다. 예측할 때마다 다시 학습할 이유가 없으니 당연한 분리인데, 그동안은 한 노트북 안에서 둘이 붙어 있었다는 걸 이제야 의식했다.

class IrisInput(BaseModel): # 요청 본문의 타입까지 여기서 검증된다 sepal_length: float sepal_width: float petal_length: float petal_width: float @app.post('/predict') def predict(data: IrisInput): prediction = int(model.predict([[data.sepal_length, ...]])[0]) return {'prediction': prediction, 'class_name': target_names[prediction]}

서빙은 FastAPI로 했다. 입력 형식을 클래스로 선언해두면 타입이 안 맞는 요청은 알아서 걸러지고, API 문서까지 자동으로 만들어진다. 서버가 살아 있는지 확인하는 /health를 따로 두는 것도 여기서 처음 봤는데, 뒤에 나올 컨테이너 환경에서 왜 필요한지 자연스럽게 이어졌다.

FROM python:3.12-slim WORKDIR /app COPY requirements.txt . # 의존성만 먼저 복사해서 RUN pip install --no-cache-dir -r requirements.txt # 이 층을 캐시로 재사용 COPY . . EXPOSE 8000 CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

마지막은 Docker였다. requirements.txt를 전체 코드보다 먼저 복사하는 이유가 인상적이었다. 코드만 고쳤을 때 라이브러리 설치 층을 그대로 재사용해서 빌드가 빨라진다는 설명이었는데, 두 줄 순서를 바꾸는 것만으로 빌드 시간이 달라진다는 게 흥미로웠다. 호스트에서 접속하려면 --host 0.0.0.0이 필요하다는 것, .dockerignore로 가상환경과 캐시를 빼서 이미지를 줄인다는 것도 같이 정리했다.

KPT 회고

Keep

CLIP → BLIP → 이미지를 읽는 LLM → 이미지 생성 → 멀티모달 RAG로 이어지는 흐름을 끊지 않고 따라갔다. 모델이 계속 바뀌는데도 헷갈리지 않았던 건 "이 모델은 이미지를 무엇으로 바꾸는가"를 매번 같은 기준으로 적어두면서 봤기 때문이다. 프로젝트 마무리와 발표가 겹친 주였는데도 진도를 밀리지 않고 따라간 것도 남겨둘 만하다.

Problem

동영상 RAG가 절반에서 멈췄다. 프레임을 뽑고 장면 해설까지 만들어놓고도, 정작 그걸 검색해서 답하는 단계를 해보지 못했다. 지난주 Try에 적었던 ViT 직접 구현도 손을 못 댔다. 목표를 적어두고 다음 주에 그대로 넘기는 일이 두 주째 반복되고 있다.

Try

만들어둔 프레임 캡션을 벡터 DB에 넣어 영상 질의응답까지 끝을 보려 한다. 이미 이미지로 한 번 해봤으니 오래 걸릴 일은 아니다. 그리고 FastAPI로 띄운 서비스에 Iris 대신 이번에 다룬 이미지 모델을 얹어서, 이미지를 올리면 설명이 돌아오는 형태까지 직접 만들어볼 생각이다.

새롭게 발견한 것

같은 공간에 넣으면 검색이 된다. 이미지와 문장이 하나의 벡터 공간을 공유하는 순간, 제로샷 분류든 이미지 검색이든 전부 코사인 유사도 계산으로 환원됐다. 텍스트 임베딩에서 배웠던 "가까우면 비슷하다"는 감각이 모달리티를 건너서도 그대로 통한다는 게 이번 주에 가장 크게 남았다.

멀티모달 RAG의 실체는 캡션이었다. 이미지를 위한 새로운 검색 구조가 따로 있는 게 아니라, 이미지를 텍스트 설명으로 바꿔 기존 RAG에 그대로 얹는 방식이었다. 대신 검색 단위와 보여줄 대상이 달라지기 때문에, metadata에 원본 이미지를 같이 넣어두는 설계가 필요했다. 새 기술을 배웠다기보다 이미 있는 걸 어떻게 배치하느냐의 문제였다.

모델 파일 하나와 예측 함수 하나면 서비스가 된다. 학습 코드와 서빙 코드를 나누고, 입력 형식을 정의하고, 컨테이너로 감쌌을 뿐인데 노트북 안에서만 돌던 모델이 주소를 가진 무언가가 됐다. 성능을 올리는 것과 남이 쓰게 만드는 건 완전히 다른 일이라는 걸, 프로젝트에서 배포를 겪고 난 뒤에 수업으로 다시 정리하니 더 잘 들어왔다.

프로젝트 진행 과정

3차 팀 프로젝트 "창업ON"을 이번 주에 마무리하고 발표까지 끝냈다. 지난주 통합을 마친 뒤라 이번 주는 실제로 써보면서 나오는 문제를 잡고, 마지막으로 성능을 다시 재는 데 집중했다.

  • 시연 결함 정리 — 직접 써보며 나온 사용성 문제를 따로 목록으로 모아 처리했다. 채팅 답변의 마크다운이 평문으로 나오던 것, 계정을 바꿔도 대화방과 로드맵 진행률이 남던 것, 저장한 공고가 페이지를 옮기면 사라지던 것 등이었다
  • 응답 속도 — 세금 질문에 의미가 비슷한 질문의 검색·판정 결과를 재사용하는 캐시를 붙여, 같은 평가셋 기준 평균 응답을 17.69초에서 12.46초로 줄였다(29.6% 단축). 통과율 77.4%는 그대로 유지했으니, 정확도를 깎지 않고 대기 시간만 줄인 셈이다
  • 최종 평가 — 최종 코드로 250건 평가를 다시 돌려 전체 통과율이 78.0%에서 84.8%로 올랐다. 정책 검색 재현율은 73.0%, 세금 답변 통과율은 80.6%였다

발표를 마친 뒤 코드를 다음 프로젝트 저장소로 옮기면서 3차를 닫았다. 마지막까지 남은 미해결 항목도 몇 개 있었는데, 그걸 숨기지 않고 상태 문서에 그대로 적어둔 게 오히려 정리에 도움이 됐다.
